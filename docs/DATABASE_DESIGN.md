# Database Design and Normalization

## Design goals

The database supports authentication, Bangladesh location data, tourist spot discovery, many-to-many spot categories, ratings, vehicle pricing, travel guides, bookings, trip plans, route analytics, user milestones and audit logs.

All major entities use UUID primary keys stored as `CHAR(36)`. UUIDs are generated by the backend with Node's `crypto.randomUUID()`.

## Tables

1. `users` — account, role and status
2. `refresh_tokens` — revocable sessions for logout
3. `divisions` — Bangladesh divisions
4. `districts` — districts linked to divisions
5. `spot_categories` — reusable categories
6. `tourist_spots` — main spot information and coordinates
7. `tourist_spot_categories` — many-to-many spot/category junction
8. `spot_images` — multiple images for each spot
9. `spot_ratings` — one rating per user per spot
10. `vehicles` — vehicle pricing and recommendation data
11. `travel_guides` — guide profiles
12. `trip_plans` — user trip header
13. `trip_plan_stops` — ordered spots in a trip
14. `guide_bookings` — guide reservation records
15. `route_recommendation_logs` — route analytics data
16. `user_milestones` — calculated travel progress
17. `activity_logs` — API and audit records

## Normalization

### First Normal Form

Columns hold atomic values. Repeating images, stops, ratings and categories are not stored inside a tourist spot row. They use separate related tables.

### Second Normal Form

The junction table `tourist_spot_categories` uses the combined key `(spot_id, category_id)` and contains no attributes that depend on only one side of the relationship.

### Third Normal Form

Division names are not duplicated in tourist spots. A spot references a district, and a district references a division. Guide and vehicle records reference districts by ID. Category descriptions are stored once in `spot_categories`.

## Key constraints

- Unique email and phone for users
- Unique category and spot slugs
- Unique user rating per tourist spot
- Unique stop order and spot within a trip
- Latitude and longitude range checks
- Rating values restricted to 1–5
- Non-negative fares and costs
- Trip end date cannot be earlier than start date
- Delete behavior selected according to business rules

## Foreign-key delete rules

- User sessions and trip plans cascade when a user is deleted
- Spot images and ratings cascade when a spot is deleted
- Historical trip stop references restrict spot deletion
- Vehicle and guide references in trips become `NULL` when those records are removed
- Audit log user references become `NULL` to preserve history
